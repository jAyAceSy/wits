# WITS — Warehouse Inventory Transfer System

A simple, cloud-based replacement for the paper-based inventory transfer
process between Production and Warehouse. Warehouse staff scan barcodes
(Honeywell / USB / Bluetooth handheld scanners, which behave like a
keyboard) to build a transfer, then submit it — everything is saved to
the cloud immediately.

**Stack:** React + TypeScript + Vite + Tailwind CSS · Supabase (Postgres,
Auth, Row Level Security, Edge Functions) · Vercel hosting.

---

## 1. How it works (at a glance)

1. User logs in.
2. **New Transfer** → the app immediately creates a *draft* transfer row
   in the database and shows its auto-generated **Transfer Number**,
   **Date**, and **Time Stamp**.
3. User fills in **Warehouse Receiver**, **Production Area**,
   **Destination Warehouse**, and optional **Remarks**.
4. User scans a barcode. The app looks it up in the **Products** master
   table and auto-fills **Item Code**, **Description**, **UOM**, then
   moves focus straight to **Quantity**.
5. User enters the quantity and clicks **Add Item** (or presses Enter).
   The line is written to the database immediately, and focus returns to
   the barcode field — no mouse needed for continuous scanning.
6. Duplicate barcodes in the same transfer are rejected (both in the UI
   and by a database constraint). Unknown barcodes show an "Unknown
   Barcode" message and are not added.
7. **Submit Transfer** finalizes the record (status `draft` →
   `submitted`). A database trigger refuses to submit if required header
   fields are missing or no items were scanned.

Every scan is written to Postgres the moment "Add Item" is clicked — not
batched client-side — so nothing is lost if a device loses power or the
browser is closed mid-transfer.

## 3. Database schema

Five tables only, as scoped:

| Table               | Purpose                                                             |
|----------------------|----------------------------------------------------------------------|
| `users`              | Profile + role for each Supabase Auth user (`admin` / `warehouse_staff`) |
| `products`           | The single master table: barcode, item code, description, UOM       |
| `transfer_headers`   | One row per transfer (auto number/date/timestamp, status, totals)    |
| `transfer_details`   | One row per scanned line item (unique per transfer+barcode)          |
| `audit_logs`         | Automatic change history for products, transfers, and users          |

Key automation, all done in Postgres so the frontend stays simple:

- **Transfer numbers** (`TRF-YYYYMMDD-00001`) are generated by a
  `BEFORE INSERT` trigger — the client never invents one.
- **Header totals** (`total_items`, `total_qty`) are recalculated by a
  trigger every time a line is added/edited/removed.
- **Duplicate barcodes** within a transfer are blocked by a
  `UNIQUE (transfer_id, barcode)` constraint.
- **Submit validation** (required header fields + at least one item) is
  enforced by a trigger, so it can't be bypassed by a buggy client.
- **Row Level Security** ensures warehouse staff can only see their own
  transfers; admins can see everything; only admins can manage Products
  and Users.

## 4. Setup

### 4.1 Create the Supabase project

1. Go to [supabase.com](https://supabase.com) → **New project**.
2. Once it's provisioned, open **Project Settings → API** and copy:
   - **Project URL**
   - **anon public key**

### 4.2 Run the database schema

1. Open **SQL Editor** in the Supabase dashboard.
2. Paste the contents of `supabase/schema.sql` and run it.
3. (Optional) Paste and run `supabase/seed.sql` for sample products.

### 4.3 Create the first Administrator

The anon key can't create login accounts directly (that requires the
service role key, which must never reach the browser). Create the first
admin from the dashboard:

1. **Authentication → Users → Add user → Create new user**
2. Email + a temporary password
3. Under **User Metadata**, add JSON:
   ```json
   { "full_name": "Warehouse Admin", "role": "admin" }
   ```
4. A database trigger automatically creates the matching `public.users`
   row with `role = 'admin'`.

From then on, that admin can invite more users from the **Users** page in
the app (see §4.5).

### 4.4 Configure the frontend

```bash
cp .env.example .env
```

Edit `.env`:

```
VITE_SUPABASE_URL=https://YOUR-PROJECT-REF.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR-ANON-KEY
```

Install and run:

```bash
npm install
npm run dev
```

Visit `http://localhost:5173` and sign in with the admin account you
created.

### 4.5 (Optional) Deploy the "Invite User" Edge Function

This lets admins invite new users from inside the app instead of via the
Supabase dashboard. Requires the [Supabase CLI](https://supabase.com/docs/guides/cli).

```bash
supabase login
supabase link --project-ref YOUR-PROJECT-REF
supabase functions deploy invite-user
```

The function reads `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and
`SUPABASE_SERVICE_ROLE_KEY` from the Supabase-managed environment — you
don't need to set these yourself; Supabase injects them automatically for
Edge Functions.

If you skip this step, just keep creating users from **Authentication →
Users** in the dashboard (same result — the `handle_new_auth_user`
trigger takes care of the rest).

## 5. Deploying to Vercel

1. Push this project to a GitHub/GitLab/Bitbucket repo.
2. In [Vercel](https://vercel.com), **Add New → Project**, import the repo.
3. Framework preset: **Vite**. Build command `npm run build`, output
   directory `dist` (Vercel usually detects this automatically).
4. Add environment variables in **Project Settings → Environment
   Variables**:
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY`
5. Deploy. `vercel.json` already includes the SPA rewrite rule so
   client-side routes (e.g. `/transfers/123`) work on refresh.

The app is a static SPA talking directly to Supabase over HTTPS, so any
number of warehouse users can use it simultaneously from any device with
a browser — no server to scale.

## 6. Barcode scanner notes

Honeywell handheld scanners, USB scanners, and Bluetooth scanners in this
setup all operate in **keyboard-wedge (HID) mode**: they simply "type"
the barcode characters into whatever field is focused, then send an
Enter keystroke. WITS is built around that:

- The barcode field on **New Transfer** is auto-focused on page load.
- The `useBarcodeScannerFocus` hook re-focuses that field whenever focus
  drifts somewhere non-interactive, so scanning works continuously
  without touching the mouse.
- Pressing Enter in the barcode field triggers the product lookup;
  pressing Enter in the Quantity field triggers **Add Item**; after
  adding, focus returns to the barcode field automatically.
- If your scanner's default configuration doesn't send an Enter/Tab
  suffix, configure it to append a **Carriage Return (CR)** after each
  scan (this is a one-time setting in the scanner's configuration
  barcode sheet, standard on Honeywell devices).

No custom scanner SDK or native app is required — this works over a
regular web browser on desktop or mobile.

## 7. Roles

| Capability                        | Admin | Warehouse Staff |
|------------------------------------|:-----:|:----------------:|
| Create / scan / submit transfers   | ✅    | ✅               |
| View own transfer history          | ✅    | ✅               |
| View **all** transfers             | ✅    | —                |
| Manage Products (add/edit/delete/import) | ✅ | — |
| Manage Users                        | ✅    | —                |
| Reports & exports (Excel/PDF)       | ✅    | —                |

Enforced both in the UI (route guards) and at the database level (Row
Level Security) — a warehouse staff account cannot read another user's
transfers even by calling the API directly.

## 8. Importing products from Excel

On the **Products** page, click **Import from Excel** and choose an
`.xlsx`/`.xls`/`.csv` file with these column headers (case-insensitive):

| Barcode | Item Code | Description | UOM |
|---------|-----------|-------------|-----|

Existing barcodes are updated (upsert); new barcodes are inserted.

## 10. Regenerating types after a schema change

`src/lib/database.types.ts` is hand-written to mirror `supabase/schema.sql`.
If you modify the schema, either update that file to match, or regenerate
it with the Supabase CLI:

```bash
supabase gen types typescript --project-id YOUR-PROJECT-REF > src/lib/database.types.ts
```
